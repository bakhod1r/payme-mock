payme-mock

A local stand for integrating against Payme. It speaks both halves of the protocol — the Subscribe API your backend calls, and the Merchant API the provider calls back — so an integration can be driven end to end without a real cashbox, a real card, or a network.

It is not a stub. Payments hold state, cards can be rigged to fail the way real cards fail, and every call in and out is recorded with both bodies and both header sets.

Not affiliated with Payme or Paycom. An independent testing tool built from the public protocol documentation. Do not put real card numbers or production keys in it.

What it is for

Three things are hard to rehearse against a real sandbox.

Failures on demand

A blocked card, an expired card, a ten-second timeout, a malformed response, a dropped connection, a webhook delivered twice. Each is a rule you switch on.

The other side's view

The stand keeps the provider's record of a transaction separately from the merchant's. When the two disagree, that disagreement is visible — which is the bug class this exists for.

Repeatability

One seed file puts the whole stand back to a known state, so a run means the same thing tomorrow.

The API, in your browser

The playground runs the Subscribe API in the page itself: the same Go service the stand runs, compiled to WebAssembly and wired to memory instead of Postgres. Register a card, ask for the OTP, verify it, open a receipt and pay it — nothing is sent anywhere.

The rigging survives the move: pay with the provider's blocked test card and it is refused with -31008, and a browser credential is still turned away from the server-side methods. It is one body of code, so a rule that holds there holds here.

The console

A static snapshot, captured from a real stand after a handful of payments were driven through it — three that settled, three rigged to fail, one cancelled and one refused for a bad key. Filters and forms are inert; everything else is the console as it renders.

Dashboard

Every cashbox with its balance and what went through it, and the last calls in and out.

Payments

One row per payment, whichever halves of it exist — the provider's receipt, the merchant's transaction, or both, with the two states side by side.

Cards

Every card the stand knows, with the outcome each one is rigged to produce.

Fault rules

What is set to go wrong, on which service and method, and how often.

Traffic

Every call with both bodies and both header sets, including the ones a rule answered.

Sandboxes

The cashboxes themselves: merchant ids, keys, kind and merchant group.

Services

ServicePortWhat it is
paymemock8082 The provider side: the Subscribe API server, the checkout emulator, and the caller of your Merchant API. Nothing it returns says it is a mock.
merchant8081 An example merchant: the endpoint the provider calls, with payers, orders and transactions behind it. The reference for what your own endpoint has to do.
console8080 The control UI: sandboxes, cards, payments, fault rules, the IP allowlist and the live traffic log.

Quick start

  1. Clone it and set a console password — the console shows every sandbox's keys, so it refuses to start without one. 
    git clone https://github.com/bakhod1r/payme-mock.git
cd payme-mock
cp .env.example .env
$EDITOR .env          # set CONSOLE_PASSWORD
  2. Bring the stand up. 
    make up
    The console is on http://127.0.0.1:8080, bound to loopback deliberately.
  3. Load the example integration — three cashboxes, a payer each, and the provider's published test cards. 
    docker compose exec -T postgres psql -U payme -d paymemock \
  < seed/example_cashboxes.sql
  4. Point your backend's Subscribe base URL at http://localhost:8082/api and give it a sandbox's merchant id and test key. Nothing else in your code changes: swapping the base URL back to the real provider runs the same code against it.

Rigging a card

Every card carries an outcome that decides what happens when it is used.

OutcomeWhat the caller sees
successThe payment goes through.
insufficient_fundsDeclined for money.
blockedCard blocked.
expiredCard expired.
verify_failedThe OTP is never accepted.
system_errorAn unattributed processing failure.

Independently of the outcome: delay_ms holds the answer back, sms_enabled withholds the OTP, and frozen keeps a payment from ever settling. The stand's shared OTP is 666666.

Fault injection

A rule matches on service, method (globs allowed: receipts.*, *Transaction), the account object, the transaction id and an amount range — and then does one thing.

delay · rpc_error · http_status · malformed · drop · duplicate · passthrough

Rules are ordered by priority and the first match wins, so a broad rule can sit behind a narrow one. probability and times_left make a rule intermittent, which is what a retry path actually has to survive. Every call answered by a rule is marked as such in the traffic log, so a deliberate failure is never mistaken for a real one.
